# Рекомендации по портированию и выпуску

На этой странице собраны полезные рекомендации и чеклист того, что стоит учитывать при выпуске игры или при переносе её на новую платформу.

Портирование игры на Defold на новую платформу или первый релиз обычно представляет собой довольно простой процесс. Теоретически достаточно убедиться, что соответствующие разделы настроены в файле *game.project*, но чтобы максимально использовать возможности каждой платформы, рекомендуется адаптировать игру под её особенности.


## Ввод
Обязательно адаптируйте игру под методы ввода конкретной платформы. Подумайте о добавлении поддержки [геймпадов](/manuals/input-gamepads), если платформа их поддерживает. Также убедитесь, что в игре есть меню паузы: если контроллер внезапно отключится, игра должна быть поставлена на паузу.

## Локализация
Переведите весь текст в игре. Для релиза в Европе и Америке стоит как минимум поддержать EFIGS (английский, французский, итальянский, немецкий и испанский). Убедитесь, что в игре можно легко переключаться между разными языками, например через меню паузы.

::: important
Только для iOS: обязательно укажите [Localizations](/manuals/project-settings/#localizations) в `game.project`, поскольку `sys.get_info()` никогда не вернёт язык, которого нет в этом списке.
:::

Переведите текст на странице магазина: это положительно влияет на продажи. На некоторых платформах наличие перевода текста страницы магазина на язык каждой страны, где доступна игра, является обязательным.

## Материалы для магазина

### Иконка приложения
Позаботьтесь о том, чтобы игра выделялась среди конкурентов. Иконка часто становится первой точкой контакта с потенциальными игроками. Её должно быть легко заметить на странице, полной игровых иконок.

### Баннеры и изображения для магазина
Используйте выразительный и привлекательный арт для игры. Вероятно, стоит потратить немного денег на работу с художником, чтобы создать визуальные материалы, которые будут привлекать игроков.


## Сохранения

### Сохранения на десктопе, мобильных устройствах и в вебе
Сохранения и другие данные состояния можно хранить с помощью функции API Defold `sys.save(filename, data)` и загружать через `sys.load(filename)`. Для получения пути к специфичному для ОС месту хранения файлов, обычно в домашней директории текущего пользователя, можно использовать `sys.get_save_file(application_id, name)`.

### Сохранения на консолях
Использование `sys.get_save_file()` и `sys.save()` хорошо работает на большинстве платформ, но на консолях рекомендуется использовать другой подход. Консольные платформы обычно связывают пользователя с каждым подключённым контроллером, поэтому сохранения, достижения и другие возможности должны быть привязаны к соответствующему пользователю.

События ввода с геймпада содержат идентификатор пользователя, который можно использовать для связывания действий контроллера с пользователем на консоли.

Консольные платформы и их нативные расширения предоставляют специфичные для платформы функции API для сохранения и загрузки данных, связанных с конкретным пользователем. Используйте эти API для работы с сохранениями на консолях.

API файловых операций на консолях, как правило, асинхронны. При разработке кроссплатформенной игры с поддержкой консолей рекомендуется изначально проектировать её так, чтобы все файловые операции были асинхронными независимо от платформы. Например:

```lua
local function save_game(data, user_id, cb)
	if console then
		local filename = "savegame"
		consoleapi.save(user_id, filename, data, cb)
	else
		local filename = sys.get_save_file("mygame", "savegame" .. user_id)
		local success = sys.save(filename, data)
		cb(success)
	end
end
```


## Артефакты сборки

Обязательно [генерируйте отладочные символы](/manuals/debugging-native-code/#symbolicate-a-callstack) для каждой выпущенной версии, чтобы иметь возможность разбирать падения приложения. Храните их вместе со сборкой приложения.

## Оптимизация приложения

Прочитайте [руководство по оптимизации](/manuals/optimization), чтобы узнать, как оптимизировать приложение по производительности, размеру, потреблению памяти и батареи.



## Производительность
Всегда тестируйте на целевом железе. Проверьте производительность игры и при необходимости оптимизируйте её. Используйте [профилировщик](/manuals/profiling), чтобы находить узкие места в коде.


## Разрешение экрана и частота обновления
Для платформ с фиксированной ориентацией и разрешением экрана: убедитесь, что игра корректно работает при целевом разрешении и соотношении сторон. Для платформ с переменным разрешением и соотношением сторон: убедитесь, что игра корректно работает при разных разрешениях и соотношениях сторон. Учитывайте, какой [view projection](/manuals/render/#default-view-projection) используется в рендер-скрипте и камере.

Для мобильных платформ либо зафиксируйте ориентацию экрана в *game.project*, либо убедитесь, что игра одинаково хорошо работает и в горизонтальном, и в вертикальном режиме.

* **Размеры экрана** - Всё ли выглядит хорошо на большем или меньшем экране по сравнению со стандартной шириной и высотой, заданными в *game.project*?
  * Здесь будут играть роль проекция, используемая в рендер-скрипте, и макеты, используемые в GUI.
* **Соотношения сторон** - Всё ли выглядит хорошо на экране с соотношением сторон, отличающимся от стандартного соотношения, полученного из ширины и высоты в *game.project*?
  * Здесь будут играть роль проекция, используемая в рендер-скрипте, и макеты, используемые в GUI.
* **Частота обновления** - Хорошо ли игра работает на экране с частотой обновления выше 60 Гц?
  * Имеют значение `vsync` и `swap interval` в разделе Display файла *game.project*

## Мобильные телефоны с вырезом и камерами в отверстии экрана
Использование небольших вырезов в экране для фронтальной камеры и датчиков (notch или hole punch) стало очень распространённым. При переносе игры на мобильные платформы размещайте критически важную информацию внутри безопасной области платформы.

Defold имеет встроенную поддержку безопасной области на Android и iOS. Параметр `gui.safe_area_mode` в *game.project* определяет, какие противоположные отступы безопасной области влияют на корректировку GUI. Значение по умолчанию `none` игнорирует отступы; `long` применяет левый и правый отступы в альбомной ориентации и верхний и нижний в портретной; `short` применяет противоположную пару; `both` применяет все четыре края. GUI-скрипт может переопределить общий режим проекта для своей сцены с помощью [`gui.set_safe_area_mode()`](/ref/gui/#gui.set_safe_area_mode). Для пользовательской логики GUI или рендеринга функция [`window.get_safe_area()`](/ref/window/#window.get_safe_area) возвращает безопасный прямоугольник и отдельные отступы каждого края. Платформы без встроенных отступов безопасной области возвращают всё окно и нулевые отступы.

[Расширение Safe Area](/extension-safearea) остаётся альтернативой для старых проектов или процессов, которым требуется поведение сверх встроенных API; для стандартной обработки безопасной области Android и iOS оно не нужно.


### Зарезервированные области экрана {#reserved-screen-areas}

[`window.get_reserved_areas()`](/ref/window/#window.get_reserved_areas) сообщает об отдельных областях, перекрывающих окно игры, например вырезах камеры и Dynamic Island. Используйте эти прямоугольники для размещения содержимого вокруг отдельных препятствий. Используйте `window.get_safe_area()`, когда нужен единый безопасный прямоугольник макета и его краевые отступы.

Результат — массив таблиц с полями `x`, `y`, `width` и `height`. Каждый прямоугольник обрезан по границам окна игры. Начало координат — в левом нижнем углу: `x` задаёт левый край, `y` — нижний, в пикселях окна, соответствующих [`window.get_size()`](/ref/window/#window.get_size). Эти координаты не зависят от адаптации GUI и логического разрешения в *game.project*, поэтому перед использованием их как позиций нод учитывайте преобразования GUI.

Поддержка платформ:

- **iOS 27.1 и новее:** активные перекрытия, сообщаемые UIKit, включая его отступы взаимодействия.
- **Android 9 (уровень API 28) и новее:** прямоугольники вырезов дисплея.

На неподдерживаемых платформах и версиях ОС, а также при отсутствии сообщаемых препятствий функция возвращает пустую таблицу. Пустая таблица не означает, что всё окно безопасно для важного содержимого: складки, системные панели, клавиатуры и области жестов не входят в этот API. Для безопасного прямоугольника платформы используйте `window.get_safe_area()`.

### Обновление областей после событий окна {#refreshing-areas-after-window-events}

Запрашивайте зарезервированные области при инициализации и снова в каждом callback [`window.WINDOW_EVENT_RESIZED`](/ref/window/#window.WINDOW_EVENT_RESIZED). После первого запроса изменения геометрии зарезервированных областей также вызывают это событие на поддерживаемых платформах, даже если размер окна не меняется. Каждая возвращённая таблица — снимок состояния; сохранённые таблицы не обновляются автоматически.

На iOS это событие также отправляется после переходов ориентации и изменений отступов безопасной области. Поворот на 180° в альбомной ориентации может переместить вырез камеры или Dynamic Island на другую сторону, сохранив размеры окна и отступы безопасной области. Обновляйте геометрию при событии, даже если `data.width` и `data.height` равны прежним значениям.

Следующий скрипт поддерживает актуальность обоих наборов геометрии:

```lua
local function refresh_screen_areas(self)
    self.safe_area = window.get_safe_area()
    self.reserved_areas = window.get_reserved_areas()
    -- Обновить интерфейс с учётом нового безопасного прямоугольника и зарезервированных областей.
end

local function on_window_event(self, event, data)
    if event == window.WINDOW_EVENT_RESIZED then
        -- Обновить данные, даже если ширина и высота не изменились.
        refresh_screen_areas(self)
    end
end

function init(self)
    refresh_screen_areas(self)
    window.set_listener(on_window_event)
end

function final(self)
    window.set_listener(nil)
end
```

Одновременно можно зарегистрировать только один слушатель событий окна. Если в игре уже есть такой слушатель, добавьте в него эту логику обновления. Замена сохранённого массива при каждом обновлении также удаляет устаревшие прямоугольники, когда результат становится пустым.

## Рекомендации для конкретных платформ

### Android
Обязательно храните свой [keystore](/manuals/android/#creating-a-keystore) в надёжном месте, чтобы вы могли обновлять игру.


### Консоли
Сохраняйте полный комплект файлов сборки для каждой версии. Они понадобятся, если вы захотите выпускать патчи для игры.


### Nintendo Switch
Интегрируйте код, специфичный для платформы. Для Nintendo Switch существует отдельное расширение со вспомогательной функциональностью для выбора пользователя и т.д.

Defold для Nintendo Switch использует Vulkan в качестве графического бэкенда — обязательно протестируйте игру с [графическим бэкендом Vulkan](https://github.com/defold/extension-vulkan).


### PlayStation®4
Интегрируйте код, специфичный для платформы. Для PlayStation®4 существует отдельное расширение со вспомогательной функциональностью для выбора пользователя и т.д.


### HTML5
Популярность веб-игр на мобильных телефонах растёт, поэтому стоит постараться сделать игру хорошо работающей и в мобильном браузере. Также важно помнить, что веб-игры должны быстро загружаться. Обязательно оптимизируйте игру по размеру. Кроме того, продумайте процесс загрузки в целом, чтобы не терять игроков без необходимости.

В 2018 году браузеры ввели политику autoplay для звуков, которая запрещает играм и другому веб-контенту воспроизводить звук до первого пользовательского взаимодействия (касание, нажатие кнопки, действие с геймпада и т.д.). При переносе на HTML5 важно учитывать это и начинать воспроизведение звуков и музыки только после первого взаимодействия пользователя. Попытки воспроизводить звук до такого взаимодействия будут записываться как ошибка в консоли разработчика браузера, но не повлияют на работу игры.

Также обязательно ставьте на паузу все воспроизводимые звуки, если игра показывает рекламу.
