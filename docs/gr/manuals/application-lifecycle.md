# Κύκλος ζωής εφαρμογής {#application-lifecycle}

Ο κύκλος ζωής μιας εφαρμογής ή ενός παιχνιδιού Defold είναι, σε γενικές γραμμές, απλός. Η μηχανή περνά από τρία στάδια εκτέλεσης: αρχικοποίηση, βρόχο ενημέρωσης (όπου οι εφαρμογές και τα παιχνίδια περνούν το μεγαλύτερο μέρος του χρόνου τους) και οριστικοποίηση.

::: sidenote
Το εγχειρίδιο αφορά το Defold από την έκδοση 1.12.0 και μετά. Στην έκδοση 1.12.0 εισήχθησαν αλλαγές στον κύκλο ζωής και η νέα συνάρτηση `late_update()`.
:::

![Επισκόπηση κύκλου ζωής](images/application_lifecycle/application_lifecycle.png)

Σε πολλές περιπτώσεις απαιτείται μόνο μια στοιχειώδης κατανόηση των εσωτερικών λειτουργιών του Defold. Ωστόσο, μπορεί να συναντήσετε περιπτώσεις όπου η ακριβής σειρά με την οποία το Defold εκτελεί τις εργασίες του είναι ζωτικής σημασίας. Αυτό το έγγραφο περιγράφει πώς η μηχανή εκτελεί μια εφαρμογή από την αρχή έως το τέλος.

Η εφαρμογή ξεκινά αρχικοποιώντας ό,τι χρειάζεται για τη λειτουργία της μηχανής. Φορτώνει την κύρια συλλογή και καλεί την [`init()`](/ref/go#init) σε όλα τα φορτωμένα στοιχεία που διαθέτουν συνάρτηση Lua `init()`, δηλαδή στοιχεία script και στοιχεία GUI με σενάρια GUI. Αυτό σας επιτρέπει να εκτελέσετε προσαρμοσμένη αρχικοποίηση.

Στη συνέχεια, η εφαρμογή μπαίνει στον βρόχο ενημέρωσης, όπου περνά το μεγαλύτερο μέρος της διάρκειας ζωής της. Σε κάθε καρέ ενημερώνονται τα αντικείμενα παιχνιδιού και τα στοιχεία που περιέχουν. Καλείται η [`update()`](/ref/go#update) κάθε στοιχείου script και σεναρίου GUI. Κατά τη διάρκεια του βρόχου ενημέρωσης, τα μηνύματα αποστέλλονται στους παραλήπτες τους, οι ήχοι αναπαράγονται και όλα τα γραφικά αποδίδονται.

Κάποια στιγμή ο κύκλος ζωής της εφαρμογής τελειώνει. Πριν τερματιστεί η εφαρμογή, η μηχανή βγαίνει από τον βρόχο ενημέρωσης και εισέρχεται στο στάδιο οριστικοποίησης. Προετοιμάζει όλα τα φορτωμένα αντικείμενα παιχνιδιού για διαγραφή και καλεί την [`final()`](/ref/go#final) όλων των στοιχείων τους, επιτρέποντας προσαρμοσμένη εκκαθάριση. Έπειτα τα αντικείμενα διαγράφονται και η κύρια συλλογή εκφορτώνεται.

Τα βήματα του περάσματος [«αποστολή μηνυμάτων»](#dispatching-messages) παρουσιάζονται, για λόγους σαφήνειας, σε ξεχωριστό διάγραμμα στο τέλος αυτού του εγχειριδίου. Στα διαγράμματα επισημαίνονται με ένα μικρό εικονίδιο «φακέλου με βέλος» 📩.

## Αρχικοποίηση {#initialization}

Εδώ ξεκινά το παιχνίδι σας· είναι το πρώτο βήμα της εκτέλεσής του. Χωρίζεται σε 3 φάσεις:

![Αρχικοποίηση](images/application_lifecycle/initialization.png)

### Προαρχικοποίηση {#preinitialization}

Κατά τη φάση `Preinitialization`, η μηχανή εκτελεί πολλά βήματα πριν φορτωθεί η κύρια συλλογή (συλλογή εκκίνησης). Ρυθμίζονται το εργαλείο δημιουργίας προφίλ μνήμης, οι υποδοχές, τα γραφικά, το HID (συσκευές εισόδου), ο ήχος, η φυσική και πολλά άλλα. Επίσης φορτώνεται και ρυθμίζεται η διαμόρφωση της εφαρμογής (*game.project*).

![Προαρχικοποίηση](images/application_lifecycle/pre_init.png)

Το πρώτο σημείο εισόδου που ελέγχεται από τον χρήστη, στο τέλος της αρχικοποίησης της μηχανής, είναι η κλήση της συνάρτησης `init()` του τρέχοντος σεναρίου απόδοσης.

Στη συνέχεια φορτώνεται και αρχικοποιείται η κύρια συλλογή.

### Αρχικοποίηση συλλογής {#collection-init}

Κατά τη φάση `Collection Init`, όλα τα αντικείμενα παιχνιδιού της συλλογής εφαρμόζουν τους μετασχηματισμούς τους —μετατόπιση (αλλαγή θέσης), περιστροφή και κλιμάκωση— στα παιδιά τους. Έπειτα καλούνται όλες οι διαθέσιμες συναρτήσεις `init()` των στοιχείων.

![Αρχικοποίηση συλλογής](images/application_lifecycle/collection_init.png)

::: sidenote
Η σειρά με την οποία καλούνται οι συναρτήσεις `init()` των στοιχείων αντικειμένων παιχνιδιού δεν έχει καθοριστεί. Δεν πρέπει να υποθέσετε ότι η μηχανή αρχικοποιεί αντικείμενα της ίδιας συλλογής με συγκεκριμένη σειρά.
:::

### Στάδιο μετά την ενημέρωση κατά την αρχικοποίηση {#post-update-in-initialization}

Η μηχανή πραγματοποιεί στη συνέχεια ένα πλήρες πέρασμα `Post Update` — το ίδιο πέρασμα που εκτελείται αργότερα μετά από κάθε βήμα του `Update Loop`. Εκτελείται στο τέλος της αρχικοποίησης, επειδή ο κώδικας `init()` μπορεί να στείλει νέα μηνύματα, να δώσει εντολή σε στοιχεία factory να δημιουργήσουν αντικείμενα, να επισημάνει αντικείμενα για διαγραφή και να εκτελέσει άλλες ενέργειες.

![Στάδιο μετά την ενημέρωση](images/application_lifecycle/post_init.png)

Αυτό το πέρασμα παραδίδει μηνύματα, δημιουργεί στην πράξη τα αντικείμενα παιχνιδιού των factory και διαγράφει αντικείμενα. Το πέρασμα `Post Update` περιλαμβάνει μια ακολουθία «αποστολής μηνυμάτων» που όχι μόνο παραδίδει τα μηνύματα της ουράς, αλλά επεξεργάζεται και τα μηνύματα προς proxy συλλογής. Οι επόμενες ενημερώσεις των proxy —ενεργοποίηση, απενεργοποίηση, αρχικοποίηση, οριστικοποίηση, φόρτωση και σήμανση για εκφόρτωση— πραγματοποιούνται σε αυτά τα βήματα.

Μπορείτε να φορτώσετε ένα [proxy συλλογής](/manuals/collection-proxy) κατά τη διάρκεια της `init()`, να βεβαιωθείτε ότι όλα τα αντικείμενα που περιέχει έχουν αρχικοποιηθεί και έπειτα να εκφορτώσετε τη συλλογή μέσω του proxy — όλα αυτά πριν από την πρώτη κλήση της `update()` ενός στοιχείου, δηλαδή πριν η μηχανή φύγει από το στάδιο αρχικοποίησης και εισέλθει στον βρόχο ενημέρωσης:

```lua
function init(self)
    print("init()")
    msg.post("#collectionproxy", "load")
end

function update(self, dt)
    -- The proxy collection is unloaded before this code is reached.
    print("update()")
end

function on_message(self, message_id, message, sender)
    if message_id == hash("proxy_loaded") then
        print("proxy_loaded. Init, enable and then unload.")
        msg.post("#collectionproxy", "init")
        msg.post("#collectionproxy", "enable")
        msg.post("#collectionproxy", "unload")
        -- The proxy collection objects’ init() and final() functions
        -- are called before we reach this object’s update()
    end
end
```

## Ο βρόχος ενημέρωσης {#update-loop}

Ο βρόχος `Update Loop` διατρέχει μια συγκεκριμένη ακολουθία μία φορά ανά καρέ. Αυτή η ακολουθία χωρίζεται σε 5 κύριες φάσεις:

![Βρόχος ενημέρωσης](images/application_lifecycle/update_loop.png)

1. Είσοδος (επεξεργασία και χειρισμός)
2. Ενημέρωση (συμπεριλαμβανομένων της σταθερής, της κανονικής και της όψιμης ενημέρωσης, καθώς και των ενημερώσεων των στοιχείων της μηχανής)
3. Ενημέρωση απόδοσης
4. Στάδιο μετά την ενημέρωση (εκφόρτωση proxy συλλογής, δημιουργία και διαγραφή αντικειμένων παιχνιδιού)
5. Απόδοση καρέ (αποδίδονται τα τελικά γραφικά)

### Φάση εισόδου {#input-phase}

Η είσοδος διαβάζεται από τις διαθέσιμες συσκευές, αντιστοιχίζεται με τις [συνδέσεις εισόδου](/manuals/input) και έπειτα αποστέλλεται. Κάθε αντικείμενο παιχνιδιού που έχει αποκτήσει εστίαση εισόδου στέλνει την είσοδο στις συναρτήσεις `on_input()` όλων των στοιχείων του. Ένα αντικείμενο παιχνιδιού με ένα στοιχείο script και ένα στοιχείο GUI με σενάριο GUI λαμβάνει είσοδο στις συναρτήσεις `on_input()` και των δύο στοιχείων, εφόσον αυτές έχουν οριστεί και τα στοιχεία έχουν αποκτήσει εστίαση εισόδου.

![Φάση εισόδου](images/application_lifecycle/input_phase.png)

Κάθε αντικείμενο παιχνιδιού που έχει αποκτήσει εστίαση εισόδου και περιέχει στοιχεία proxy συλλογής προωθεί την είσοδο στα στοιχεία μέσα στη συλλογή του proxy. Η διαδικασία συνεχίζεται αναδρομικά σε ενεργοποιημένα proxy συλλογής που βρίσκονται μέσα σε άλλα ενεργοποιημένα proxy.

### Φάση ενημέρωσης {#update-phase}

Η φάση `Update` αποτελεί μέρος του `Update Loop`. Ξεκινά μία φορά για τη ριζική συλλογή και στη συνέχεια εκτελείται αναδρομικά για κάθε ενεργοποιημένο proxy συλλογής.

Μέσα σε μια συλλογή, το Defold επεξεργάζεται τις συναρτήσεις επανάκλησης ανά τύπο στοιχείου: διατρέχει όλα τα στιγμιότυπα ενός τύπου στοιχείου που υλοποιεί το αντίστοιχο στάδιο, καλεί τη συνάρτηση Lua κάθε στιγμιότυπου, παραδίδει τα μηνύματα και έπειτα προχωρά στον επόμενο τύπο στοιχείου.

Η γενική σειρά των σταδίων των συναρτήσεων επανάκλησης Lua για τα στοιχεία *script* είναι:

1. `fixed_update()` — καλείται 0..N φορές ανά καρέ (αν χρησιμοποιείται σταθερό χρονικό βήμα)
2. `update()` — καλείται 1 φορά ανά καρέ
3. `late_update()` — καλείται 1 φορά ανά καρέ

![Φάση ενημέρωσης](images/application_lifecycle/update_phase.png)


Η μηχανή διατρέχει κάθε στοιχείο αντικειμένου παιχνιδιού στην κύρια συλλογή. Αν ένα από αυτά τα στοιχεία διαθέτει script με συνάρτηση `fixed_update()`/`update()`/`late_update()`, η συνάρτηση καλείται. Αν το στοιχείο είναι proxy συλλογής, κάθε στοιχείο στη συλλογή του proxy ενημερώνεται αναδρομικά, ακολουθώντας όλα τα βήματα της φάσης `Update`.

::: sidenote
Η σειρά με την οποία καλούνται οι συναρτήσεις `update()` των στοιχείων αντικειμένων παιχνιδιού δεν έχει καθοριστεί. Δεν πρέπει να υποθέσετε ότι η μηχανή ενημερώνει αντικείμενα της ίδιας συλλογής με συγκεκριμένη σειρά. Το ίδιο ισχύει για τις `fixed_update()` και `late_update()`.
:::

#### Φυσική {#physics}

Για τα στοιχεία αντικειμένων σύγκρουσης, τα μηνύματα φυσικής —συγκρούσεις, trigger, αποκρίσεις ray cast κ.λπ.— αποστέλλονται σε ολόκληρο το αντικείμενο παιχνιδιού και σε όλα τα στοιχεία που περιέχουν script με συνάρτηση `on_message()`.

Αν η προσομοίωση φυσικής χρησιμοποιεί [σταθερό χρονικό βήμα](/manuals/physics/#physics-updates), μπορεί επίσης να καλείται η συνάρτηση `fixed_update()` σε όλα τα στοιχεία script. Αυτή η συνάρτηση είναι χρήσιμη σε παιχνίδια που βασίζονται στη φυσική, όταν θέλετε να χειρίζεστε αντικείμενα φυσικής σε τακτικά διαστήματα για σταθερή προσομοίωση.

#### Μετασχηματισμοί {#transforms}

Πριν από **κάθε** ενημέρωση τύπου στοιχείου, πολλές φορές κατά τη διάρκεια του `Update Loop`, οι μετασχηματισμοί ενημερώνονται εφόσον χρειάζεται. Κάθε μετατόπιση, περιστροφή και κλιμάκωση ενός αντικειμένου παιχνιδιού εφαρμόζεται στα στοιχεία του και στα στοιχεία των παιδικών αντικειμένων παιχνιδιού.

Στο τέλος του `Update Loop` πραγματοποιείται ακόμη μία τελική ενημέρωση των μετασχηματισμών, εφόσον χρειάζεται.

#### Φάση ενημέρωσης μηχανής χωρίς σταθερές ενημερώσεις {#engine-update-phase-no-fixed-updates}

Οι παρακάτω πίνακες περιγράφουν τα περάσματα ενημέρωσης *σε επίπεδο μηχανής*. Παραλείπουν σκόπιμα την ακριβή εσωτερική σειρά προτεραιότητας των στοιχείων, η οποία αποτελεί λεπτομέρεια υλοποίησης της μηχανής, αλλά αποτυπώνουν τις εγγυήσεις σειράς που αφορούν τα script:

- η `fixed_update()` εκτελείται πριν από την `update()`
- η `late_update()` εκτελείται μετά την `update()`
- τα μηνύματα παραδίδονται μεταξύ των ενημερώσεων διαφορετικών τύπων στοιχείων, καθώς και μεταξύ των σταδίων των συναρτήσεων επανάκλησης των script

Όταν το `Use Fixed Timestep` είναι `false` ή/και το Fixed Update Frequency είναι `0`, στην αρχή της φάσης προετοιμάζεται το `dt` και έπειτα η εκτέλεση ακολουθεί τον παρακάτω πίνακα:

:::sidenote
Μετά την ενημέρωση **κάθε** τύπου στοιχείου αποστέλλονται όλα τα μηνύματα. Αυτό δεν σημειώνεται στον πίνακα για να παραμένει ευανάγνωστος.
:::

| Βήμα | Φάση μηχανής | Συνάρτηση επανάκλησης Lua | Σχόλιο |
|-|-|-|-|
| 1 | **Ενημέρωση** | `update()` | Καλείται μία φορά ανά καρέ για κάθε τύπο στοιχείου που υλοποιεί το Update, με την εσωτερική σειρά προτεραιότητας. Εδώ ενημερώνονται επίσης οι κινήσεις ιδιοτήτων αντικειμένων παιχνιδιού που ξεκίνησαν με `go.animate()`, ως ξεχωριστός τύπος στοιχείου. Τα στοιχεία **φυσικής** ενημερώνονται εδώ. Για κάθε ενεργοποιημένο proxy συλλογής, ολόκληρη η φάση `Update` καλείται αναδρομικά από το βήμα 1. |
| 2 | **Όψιμη ενημέρωση** | `late_update()` | Καλείται μία φορά ανά καρέ για κάθε τύπο στοιχείου που υλοποιεί το Late Update, με την εσωτερική σειρά προτεραιότητας. |
| 3 | **Μετασχηματισμοί** | | Πραγματοποιείται ακόμη μία τελική ενημέρωση μετασχηματισμών στο τέλος για κάθε στοιχείο, εφόσον χρειάζεται. |

#### Φάση ενημέρωσης μηχανής με σταθερό χρονικό βήμα {#engine-update-phase-with-fixed-timestep}

Όταν το `Use Fixed Timestep` είναι `true` και το Fixed Update Frequency δεν είναι μηδέν, στην αρχή της φάσης προετοιμάζονται τα `dt` (χρονική διαφορά), `fixed_dt` και `num_fixed_steps` (`0..N`). Το τελευταίο καθορίζει πόσες φορές θα κληθεί η σταθερή ενημέρωση, με βάση τον χρόνο από την προηγούμενη ενημέρωση, ώστε να διατηρείται σταθερή συχνότητα ενημερώσεων.

:::sidenote
Μετά την ενημέρωση **κάθε** τύπου στοιχείου αποστέλλονται όλα τα μηνύματα. Αυτό δεν σημειώνεται στον πίνακα για να παραμένει ευανάγνωστος.
:::

Έπειτα ακολουθεί η επαναλαμβανόμενη ακολουθία:

| Βήμα | Φάση μηχανής | Συνάρτηση επανάκλησης Lua | Σχόλιο |
|-|-|-|-|
| 1 | **Σταθερή ενημέρωση** | `fixed_update()` | Καλείται `0..N` φορές ανά καρέ, ανάλογα με τον χρονισμό, για κάθε τύπο στοιχείου που υλοποιεί το Fixed Update, με την εσωτερική σειρά προτεραιότητας. Περιλαμβάνει τα βήματα Fixed Update των στοιχείων *φυσικής*. |
| 2 | **Ενημέρωση** | `update()` | Καλείται μία φορά ανά καρέ για κάθε τύπο στοιχείου που υλοποιεί το Update, με την εσωτερική σειρά προτεραιότητας. Εδώ ενημερώνονται επίσης οι κινήσεις ιδιοτήτων αντικειμένων παιχνιδιού που ξεκίνησαν με `go.animate()`, ως ξεχωριστός τύπος στοιχείου. Για κάθε ενεργοποιημένο proxy συλλογής, η φάση `Update` καλείται αναδρομικά από το βήμα 1. |
| 3 | **Όψιμη ενημέρωση** | `late_update()` | Καλείται μία φορά ανά καρέ για κάθε τύπο στοιχείου που υλοποιεί το Late Update, με την εσωτερική σειρά προτεραιότητας. |
| 4 | **Μετασχηματισμοί** | | Πραγματοποιείται ακόμη μία τελική ενημέρωση μετασχηματισμών στο τέλος για κάθε στοιχείο, εφόσον χρειάζεται. |

Αν χρειάζεστε περισσότερες λεπτομέρειες για την εσωτερική λειτουργία του Defold κατά τη φάση Update, αξίζει να διαβάσετε τον ίδιο τον κώδικα του [`gameobject.cpp`](https://github.com/defold/defold/blob/dev/engine/gameobject/src/gameobject/gameobject.cpp).

### Φάση ενημέρωσης απόδοσης {#render-update-phase}

Το μπλοκ ενημέρωσης απόδοσης αποστέλλει πρώτα όλα τα μηνύματα στην υποδοχή (socket) `@render`, όπως τα μηνύματα `set_view_projection` του στοιχείου κάμερας και τα μηνύματα `set_clear_color`. Στη συνέχεια καλείται η `update()` του σεναρίου απόδοσης.

![Φάση ενημέρωσης απόδοσης](images/application_lifecycle/render_update_phase.png)

### Φάση μετά την ενημέρωση {#post-update-phase}

Μετά τις ενημερώσεις εκτελείται το στάδιο «μετά την ενημέρωση» (post update). Σε αυτό το στάδιο εκφορτώνονται από τη μνήμη τα proxy συλλογής που έχουν επισημανθεί για εκφόρτωση, κάτι που συμβαίνει κατά την ακολουθία «αποστολή μηνυμάτων». Κάθε αντικείμενο παιχνιδιού που έχει επισημανθεί για διαγραφή καλεί όλες τις διαθέσιμες συναρτήσεις `final()` των στοιχείων του. Ο κώδικας στις συναρτήσεις `final()` στέλνει συχνά νέα μηνύματα στην ουρά, οπότε εκτελείται ακόμη ένα πέρασμα «αποστολής μηνυμάτων».

![Φάση μετά την ενημέρωση](images/application_lifecycle/post_update_phase.png)

Κάθε στοιχείο factory που έχει λάβει εντολή να δημιουργήσει ένα αντικείμενο παιχνιδιού το δημιουργεί στη συνέχεια. Τέλος, τα αντικείμενα παιχνιδιού που έχουν επισημανθεί για διαγραφή διαγράφονται πραγματικά.

### Φάση απόδοσης {#render-phase}

Το τελευταίο βήμα του βρόχου ενημέρωσης περιλαμβάνει την αποστολή μηνυμάτων στην υποδοχή `@system`, όπως τα `exit` και `reboot`, την ενεργοποίηση ή απενεργοποίηση του profiler και την έναρξη ή διακοπή της καταγραφής βίντεο.

![Φάση απόδοσης](images/application_lifecycle/render_phase.png)

Στη συνέχεια αποδίδονται τα γραφικά, καθώς και το οπτικό εργαλείο δημιουργίας προφίλ (δείτε την [τεκμηρίωση εντοπισμού σφαλμάτων](/manuals/debugging)). Μετά την απόδοση των γραφικών πραγματοποιείται η καταγραφή βίντεο.

#### Ρυθμός καρέ και χρονικό βήμα συλλογής {#frame-rate-and-collection-time-step}

Ο αριθμός των ενημερώσεων καρέ ανά δευτερόλεπτο, ο οποίος ισούται με τον αριθμό των εκτελέσεων του βρόχου ενημέρωσης, μπορεί να οριστεί στις ρυθμίσεις του έργου ή μέσω προγραμματισμού, στέλνοντας το μήνυμα `set_update_frequency` στην υποδοχή `@system`. Επιπλέον, μπορείτε να ορίσετε ξεχωριστά το χρονικό βήμα (time step) κάθε proxy συλλογής, στέλνοντάς του το μήνυμα `set_time_step`. Η αλλαγή του χρονικού βήματος μιας συλλογής δεν επηρεάζει τον ρυθμό καρέ. Επηρεάζει το χρονικό βήμα ενημέρωσης της φυσικής και τη μεταβλητή `dt` που μεταβιβάζεται στην `update()`. Επίσης, δεν αλλάζει τον αριθμό των κλήσεων της `update()` ανά καρέ — η συνάρτηση καλείται πάντα ακριβώς μία φορά.

(Για λεπτομέρειες, ανατρέξτε στο [εγχειρίδιο proxy συλλογής](/manuals/collection-proxy) και στην τεκμηρίωση του [`set_time_step`](/ref/collectionproxy#set-time-step).)

#### Περιορισμός δραστηριότητας της μηχανής {#engine-throttling}

Το Defold παρέχει ένα API περιορισμού δραστηριότητας της μηχανής που μπορεί να παραλείπει εντελώς τις ενημερώσεις της μηχανής και την απόδοση, συνεχίζοντας να ανιχνεύει είσοδο. Κάθε είσοδος επανενεργοποιεί τη μηχανή, η οποία μπορεί να επιστρέψει σε περιορισμένη δραστηριότητα μετά από μια περίοδο αναμονής.

Δείτε το API `sys.set_engine_throttle()` για λεπτομέρειες και παραδείγματα χρήσης.

## Οριστικοποίηση {#finalization}

Όταν τερματίζεται η εφαρμογή, ολοκληρώνεται πρώτα η τελευταία ακολουθία του βρόχου ενημέρωσης. Αυτή εκφορτώνει όλα τα proxy συλλογής, οριστικοποιώντας και διαγράφοντας όλα τα αντικείμενα παιχνιδιού σε κάθε συλλογή proxy.

Έπειτα η μηχανή περνά σε μια ακολουθία οριστικοποίησης που χειρίζεται την κύρια συλλογή και τα αντικείμενά της:

![Οριστικοποίηση](images/application_lifecycle/finalization.png)

Οι συναρτήσεις `final()` καλούνται πρώτα. Ακολουθεί ακόμη μία αποστολή μηνυμάτων. Τέλος, όλα τα αντικείμενα παιχνιδιού διαγράφονται και η κύρια συλλογή εκφορτώνεται.

Στο παρασκήνιο, η μηχανή κλείνει τα υποσυστήματα: η διαμόρφωση του έργου διαγράφεται, το εργαλείο δημιουργίας προφίλ μνήμης κλείνει και ούτω καθεξής.

Η εφαρμογή έχει πλέον τερματιστεί πλήρως.

## Αποστολή μηνυμάτων {#dispatching-messages}

Η **αποστολή μηνυμάτων** είναι ένα ειδικό πέρασμα που εκτελείται μετά την ενημέρωση **κάθε** τύπου στοιχείου, όπως των sprite και των script, καθώς και μετά από κάθε άλλη ενέργεια που μπορεί να στείλει μηνύματα. Κατά την εκτέλεσή του παραδίδονται όλα τα μηνύματα που έχουν συγκεντρωθεί σε μια ουρά. Αυτά τα περάσματα επισημαίνονται στα διαγράμματα με μικρά εικονίδια «φακέλου με βέλος» 📩.

![Αποστολή μηνυμάτων](images/application_lifecycle/dispatch_messages.png)

Αφού παραδοθούν όλα τα **μηνύματα χρήστη** με κλήση της `on_message()` για κάθε στοιχείο, τα ειδικά μηνύματα του Defold διεκπεραιώνονται με την ακόλουθη σειρά για κάθε proxy συλλογής, όπως φαίνεται και στο διάγραμμα:

1. Μηνύματα `load` — φορτώνουν τα proxy συλλογής που έχουν επισημανθεί για φόρτωση και στέλνουν ως απάντηση το μήνυμα `proxy_loaded`.
2. Μηνύματα `unload` — εκφορτώνουν τα proxy συλλογής που έχουν επισημανθεί για εκφόρτωση και στέλνουν ως απάντηση το μήνυμα `proxy_unloaded`.
3. Μηνύματα `init` — ενεργοποιούν τη φάση `Collection Init` για όλα τα proxy συλλογής που πρόκειται να αρχικοποιηθούν.
4. Μηνύματα `final` — καλούν την `final()` σε όλα τα στοιχεία του proxy που έχει επισημανθεί για οριστικοποίηση.
5. Μηνύματα `enable` — ενεργοποιούν το proxy συλλογής, ώστε ο βρόχος `Update Loop` να εκτελεστεί γι' αυτό στο επόμενο καρέ· αυτό καλεί έμμεσα την `init()` για κάθε στοιχείο της συλλογής.
6. Μηνύματα `disable` — απενεργοποιούν το proxy συλλογής, ώστε ο βρόχος `Update Loop` να **μην** εκτελεστεί γι' αυτό στο επόμενο καρέ· σταματούν εντελώς την εκτέλεση του `Update Loop` γι' αυτό.

Επειδή ο κώδικας `on_message()` οποιουδήποτε στοιχείου παραλήπτη μπορεί να στείλει επιπλέον μηνύματα, ο μηχανισμός αποστολής συνεχίζει να παραδίδει τα νέα μηνύματα αναδρομικά μέχρι να αδειάσει η ουρά. Υπάρχει, ωστόσο, όριο στον αριθμό των περασμάτων που πραγματοποιεί στην ουρά μηνυμάτων. Για λεπτομέρειες, δείτε τις [αλυσίδες μηνυμάτων](/manuals/message-passing).
